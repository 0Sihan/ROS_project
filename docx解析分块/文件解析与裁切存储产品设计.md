## 2. 文件解析层：Word → DocObject

### 2.1 输入范围（MVP）

对齐 `Orchestrator产品设计.md` §18.1：本期只做 `.docx`；`.doc` 先经 LibreOffice headless 转换为 `.docx` 再走本流程。WPS（`.wps`/`.et`/`.dps`）、PDF、ODT均为v2范围（技术规格表模块一1.2标注MVP=N），本文档不展开设计。

### 2.2 格式校验与完整性检查

对齐技术规格表模块一1.1：

| 校验项 | 规则 | 失败处理 |
|---|---|---|
| 真实格式检测 | magic bytes检测，不信任扩展名 | 与声明格式不符则拒绝 |
| 完整性校验 | SHA-256哈希；同哈希文件不重复解析 | 命中已有`doc_id`直接复用解析结果（生命周期区分见下方说明） |

> **v1.1 变更（同步 Orchestrator产品设计.md v3.0 §16.3 收口）**：本节的"同哈希不重复解析"和 Orchestrator §16.3 的 `DocCache`（字段 `sha256`/`doc_id`，v3.0 已统一为与本节一致的命名）描述的是同一件事，但生命周期表述曾不一致——本节写的是"同哈希文件不重复解析"，未提及有效期，读起来像是永久生效；Orchestrator §16.3 则明确 `DocCache` 有 30 天 TTL。两者需要区分的是**两个不同层面的东西**：
> - **解析产物本身**（`documents`/`paragraphs`/`figures` 表 + 对象存储中的原始文件与提取图片）：只要没有走 §25.3 的显式清理策略，在对象存储/数据库层面**永久保留**，不因时间推移而失效或被删除
> - **"是否命中直接复用"的判定缓存**（Orchestrator §16.3 的 `DocCache`）：30 天 TTL，是一层**决策层的时间窗口**——同一份文件哈希在 30 天内再次提交才会触发"跳过重新解析，直接复用"；超过 30 天后再次提交同一份文件，即使 `documents` 表中的解析产物仍然完好存在，系统也会按 TTL 过期处理，重新执行一次完整解析（不是因为旧数据不可用，而是产品策略上认为超过 30 天的重复提交大概率不再是"短期内的调试性重复提交"场景，值得重新走一遍解析确认，成本可接受）
>
> 本节描述的"命中已有 `doc_id` 直接复用"，实际生效范围以 Orchestrator §16.3 的 30 天 TTL 为准，本节原文未提及 TTL 属于表述遗漏，以此说明补齐。
| ZIP炸弹检测 | docx本质是zip包，解压前先读取zip目录项，校验解压后总大小不超过原始文件体积的合理倍数上限（如500倍，且绝对值不超过2GB） | 超限拒绝并返回明确错误码，不执行解压 |

### 2.3 DocObject 数据结构

```python
class DocObject(BaseModel):
    doc_id: str
    task_id: str
    original_filename: str
    format: str                     # docx / doc（已转换）
    sha256: str

    raw_text: str                   # 全书拼接文本，Level-0直接使用
    paragraphs: list["ParaMeta"]     # 全量段落列表
    chapters: list["ChapterMeta"]    # H1切分的章节列表
    tables: list["TableMeta"]
    figures: list["FigureMeta"]

    style_map: dict[str, str]        # 原始样式名 → 标准化H1-H6/正文/引文等
    parse_warnings: list[str]        # 解析过程中的降级/异常记录
```

### 2.4 段落提取与样式标准化

- 段落提取复用 `05测试文档/测试用例/脚本/crop_tool.py` 已验证的方法：用 `body.findall('.//w:p', NS)` 深度遍历（而非直接子节点遍历），确保含图片的空文本段落也被索引到（深度遍历与直接子节点索引不可混用，见 [[crop-tool技术笔记]]）
- 样式名标准化：中/英/自定义样式名（如"标题 1"/"Heading 1"/客户模板自定义样式名）→ 标准H1-H6；未知样式按字号+加粗特征推断层级，映射表用YAML维护，支持后续按客户模板扩展
- 段落类型初判（正文/标题/引文/图注/表注/参考文献/脚注）：与`文档分块框架产品设计.md` §6.3的`ChunkType`判定共享同一套关键词规则，DocObject阶段先做一次初判并携带到分块层，避免分块层重复解析

```python
class ParaMeta(BaseModel):
    para_id: str
    xml_para_index: int       # body.findall('.//w:p')深度遍历序号，全文档唯一且稳定，见§5.2用途
    text: str
    style_raw: str             # 原始样式名
    style_normalized: str      # 标准化后类型
    offset_start: int
    offset_end: int
    chapter_idx: int
    chapter_title: str
    para_idx_in_chapter: int
    has_image: bool
    image_ids: list[str]       # 关联FigureMeta.figure_id
```

> `xml_para_index` 是本文档新增字段，用途见 §5.2（v2 Word修订模式导出的原文定位）。`文档分块框架产品设计.md`的`ChunkMeta.para_ids`沿用原有语义不变，两套字段并存不冲突。

### 2.5 表格提取与展开

对齐技术规格表模块一1.2「表格提取与展开」：

- 提取行列结构，合并单元格展开为多行（保证每个数据格都有确定的行列坐标），保留表头与数据行的对应关系
- **保留原始合并结构**（本文档新增要求）：展开是为了让D1/D7等引擎按行读取文本，但用于§3图文块裁切和§5.3拼接还原时，需要知道"这几行原本是合并的"，否则还原表格视觉效果会错位。因此`TableMeta`额外保留`merged_cells`记录原始合并单元格坐标范围

```python
class TableMeta(BaseModel):
    table_id: str
    para_id: str               # 表格锚点段落
    rows: list[list[str]]      # 展开后的行列文本
    merged_cells: list[dict]   # [{"row_start":0,"row_end":1,"col_start":2,"col_end":2}, ...]
    caption_text: str | None
    caption_para_id: str | None
```

### 2.6 图片提取

对齐技术规格表模块一1.2「图片提取」（P1，简版：MVP做基础提取存储，不做深度视觉分析，因D7地图/图像合规检测推迟v2）：

- 复用 `crop_tool.py` 的 `extract_para_image_map`：解压docx包读取`word/_rels/document.xml.rels`建立rId→文件名映射，遍历`.//w:p`查找`a:blip`/`v:imagedata`引用，建立"段落索引→图片文件名列表"的映射
- 过滤规则：只保留真实图片扩展名（png/jpg/jpeg/gif/svg/bmp/tiff/tif），过滤wmf（通常是嵌入公式，非真实图片）
- 提取的图片写入 `extracted-images/{doc_id}/{figure_id}.png`（见§4.1），`FigureMeta`记录关联的`para_id`

```python
class FigureMeta(BaseModel):
    figure_id: str
    para_id: str                # 图片所在段落
    xml_para_index: int
    storage_path: str           # extracted-images/{doc_id}/{figure_id}.png
    filename_original: str      # docx内原始文件名（imageN.png）
    width_px: int | None
    height_px: int | None
    dpi: float | None           # 供D7-common-04分辨率检测直接读取，避免重复解析图片
    caption_text: str | None
    caption_para_id: str | None
```

## 3. 图文块裁切（D7专用，新增）

### 3.1 为什么需要单独设计

`文档分块框架产品设计.md` §8.1 五种裁切方式中列出了"图与上下文裁切"（`chunk_type=figure_with_context`），但只有一行说明"图注+前后段落合并块"，没有展开：

- 图片本体（二进制文件）怎么关联进chunk
- 表格类"图表"（D7的`chart_category=table`）展开后的行列结构怎么传给D7规则引擎（`D7图表校验产品设计.md` §5.5的`D7-table-01/02`需要读结构化行列，不是纯文本）
- 上下文范围取多大

本节补齐这部分设计，供D7引擎消费。

### 3.2 触发条件与裁切范围

| 触发条件 | 裁切范围 |
|---|---|
| 段落含图片（`ParaMeta.has_image=True`） | 图片本体 + 图注段落（若图片所在段落本身非图注，向后找最近的图注段落，通常紧邻）+ 前1段 + 后1段 |
| 段落为表格锚点（`TableMeta.para_id`） | 表格完整行列结构（含`merged_cells`）+ 表注段落 + 前1段 + 后1段 |

上下文范围沿用 `文档分块框架产品设计.md` §3.2 Level-2段落级context的做法（前后各1段，≤200字），不新增独立的overlap规则，保持全局一致。

### 3.3 figure_with_context 结构定义

```python
class FigureChunk(BaseModel):
    chunk_id: str
    level: int = 2
    type: str = "figure_with_context"
    doc_id: str
    task_id: str

    chart_category: str           # 对齐D7图表分类体系（statistical/geographic/table/...，见D7图表校验产品设计.md §4）
    figure_id: str | None          # 关联FigureMeta（图片类）
    table_id: str | None           # 关联TableMeta（表格类），二者互斥

    image_path: str | None         # MinIO图片路径（图片类）
    table_rows: list[list[str]] | None      # 展开后行列（表格类）
    table_merged_cells: list[dict] | None   # 原始合并结构（表格类，供§5.3还原用）

    caption_text: str
    caption_para_id: str
    seq_number: str | None         # 从caption_text提取的编号（如"图3-1"），供chart.seq检测直接用，避免D7重复解析

    context_prev: str | None       # ≤200字
    context_next: str | None       # ≤200字

    chapter_idx: int
    chapter_title: str
    offset_start: int              # caption段落在全书的offset，供位置追溯
    offset_end: int
```

### 3.4 图片存储与D7消费方式

- 图片二进制不进PostgreSQL，只存路径。D7引擎需要视觉分析时（v2，地图/图像合规检测），从`image_path`读取MinIO文件传给Claude Vision API
- 本期MVP D7只做`chart.seq`（编号连续性）/`chart.caption_ref`（交叉引用）/`chart.table_data`（表格结构，见`D7图表校验产品设计.md` §5.5），这些检测项**不需要**读取图片二进制内容，只需要`caption_text`/`seq_number`/`table_rows`等文本层信息，因此`FigureChunk`即使图片文件损坏或提取失败，也不影响本期D7检测（`image_path`为空时只记录`parse_warnings`，不阻断流程）

## 4. 存储层设计

### 4.1 MinIO Bucket规划

对齐技术规格表模块六6.4：

| Bucket | 路径规范 | 内容 |
|---|---|---|
| `raw-documents` | `{tenant_id}/{doc_id}/original.{ext}` | 用户上传的原始docx（及.doc转换后的docx） |
| `extracted-images` | `{doc_id}/{figure_id}.png` | 解析阶段提取的图片 |

访问策略全部私有，通过预签名URL供内部服务读取（对齐模块六6.1安全要求）。

### 4.2 PostgreSQL表设计

新增两张表，与`文档分块框架产品设计.md` §8.2的`chunks`表并存（通过`doc_id`关联）：

```sql
CREATE TABLE documents (
    doc_id              TEXT PRIMARY KEY,
    task_id             TEXT NOT NULL REFERENCES tasks(task_id),
    tenant_id           TEXT NOT NULL,
    original_filename   TEXT NOT NULL,
    format              TEXT NOT NULL,          -- docx / doc
    sha256              TEXT NOT NULL,
    storage_path        TEXT NOT NULL,          -- raw-documents/{tenant_id}/{doc_id}/original.{ext}
    parse_status        TEXT NOT NULL,          -- pending/parsing/success/failed
    parse_warnings       JSONB,
    created_at          TIMESTAMPTZ DEFAULT NOW()
);

CREATE TABLE paragraphs (
    para_id             TEXT PRIMARY KEY,
    doc_id              TEXT NOT NULL REFERENCES documents(doc_id),
    xml_para_index      INTEGER NOT NULL,        -- 见§2.4，v2 Word导出定位用
    text                TEXT NOT NULL,
    style_raw           TEXT,
    style_normalized    TEXT,
    offset_start        INTEGER NOT NULL,
    offset_end          INTEGER NOT NULL,
    chapter_idx         SMALLINT,
    chapter_title       TEXT,
    has_image           BOOLEAN DEFAULT FALSE
);
CREATE INDEX idx_paragraphs_doc ON paragraphs(doc_id);
CREATE UNIQUE INDEX idx_paragraphs_xml_index ON paragraphs(doc_id, xml_para_index);

CREATE TABLE figures (
    figure_id           TEXT PRIMARY KEY,
    doc_id              TEXT NOT NULL REFERENCES documents(doc_id),
    para_id             TEXT REFERENCES paragraphs(para_id),
    table_id            TEXT,                    -- 表格类填table_id，图片类为NULL
    chart_category      TEXT,
    storage_path        TEXT,                    -- 图片类填MinIO路径，表格类为NULL
    table_rows          JSONB,                    -- 表格类填展开后行列，图片类为NULL
    table_merged_cells  JSONB,
    caption_text        TEXT,
    seq_number          TEXT,
    width_px            INTEGER,
    height_px           INTEGER,
    dpi                 REAL
);
CREATE INDEX idx_figures_doc ON figures(doc_id);
```

> `figures`表同时承载图片类和表格类（即§3.3的`FigureChunk`落库形态），避免为表格单开一张几乎相同结构的表；用`storage_path`/`table_rows`二者是否为空区分类型。

### 4.3 解析失败降级

| 异常场景 | 处理方式 |
|---|---|
| 单段落解析异常（如局部XML结构损坏） | 跳过该段落，记录`parse_warnings`，不中断整体解析 |
| 图片提取失败（引用的媒体文件在docx包内缺失） | `figures.storage_path`置空，记录`parse_warnings`，不阻断（见§3.4） |
| 整份文件解析失败（如非法zip结构） | `documents.parse_status=failed`，任务终止并向用户返回明确错误 |

## 5. 拼接还原设计

"裁切后要能重新拼接书籍"对应两个下游场景：

### 5.1 场景一：前端问题定位高亮（本期支持）

已被`文档分块框架产品设计.md` §4完整覆盖：`chunk.offset_start`+`para_id`可反查回`DocObject.raw_text`中的精确字符位置，前端据此高亮。本文档不重复设计；§2.4新增`xml_para_index`字段**不影响**现有`offset_start/end`语义，两套定位信息并存、互不干扰。

### 5.2 场景二：Word修订模式导出（v2功能，本次预留字段）

对齐技术规格表模块八8.4「Word修订模式导出」（MVP=N，推迟v2）：将审核接受的AI建议写入原稿docx的`w:ins`/`w:del`修订标记，编辑可在Word中一键接受/拒绝。

**为什么字符offset不够**：`chunk.offset_start/end`是相对`DocObject.raw_text`（拼接后的纯文本）的字符位置，但Word修订标记必须插入到原始docx XML树中对应的`w:p`节点内部（`w:r`/`w:t`级别），offset本身不能直接映射到XML节点——需要额外一层"全书字符offset → 原始docx段落XML节点"的映射。

**本次设计方案（只做字段预留，不实现写回逻辑）**：

- §2.4已新增的`xml_para_index`就是这层映射的关键：它是段落在`body.findall('.//w:p')`深度遍历中的稳定序号，与原始docx文件的物理结构一一对应
- 解析阶段（本期）：为每个`ParaMeta`生成并持久化`xml_para_index`，成本几乎为零（解析时顺带记录，无需额外扫描）
- v2实现时：读取原始docx（`raw-documents`路径未变，文件本身也不需要重新解析全文），用`xml_para_index`直接定位到对应`w:p`节点，在其内部插入`w:ins`/`w:del`标记，写出新docx。因为v2阶段就能拿到"哪个字符offset对应哪个xml_para_index"（`paragraphs`表已有offset_start/end字段），offset→段落→xml节点的链路是完整的，无需重新设计
- 本期不做的部分：实际的`w:ins`/`w:del`生成算法、不同Word版本对修订标记XML结构的兼容性测试——留给v2启动时再设计，本文档只保证v2启动时不需要重新解析历史文档（`xml_para_index`已经落库）

### 5.3 全书结构还原（表格/图片的视觉还原）

- 表格：§2.5保留的`merged_cells`使表格即使经过"展开为多行"处理，仍可还原出原始合并单元格视觉效果（如审校报告需要嵌入表格截图/重建表格时使用）
- 图片：§2.6提取的图片本体独立存储在MinIO，与原docx解耦，`figures.storage_path`本身就是可直接复用的还原素材，不需要额外设计

## 6. 验收标准

| 验收项 | 指标 | 标准 |
|---|---|---|
| 格式校验 | ZIP炸弹拦截率 | 构造的恶意zip文件（解压后超限）100%被拒绝 |
| 完整性去重 | 重复文件识别率 | 同一文件重复上传不重复解析，命中率100% |
| 段落提取完整性 | 段落数量 | `paragraphs`表记录数与深度遍历`.//w:p`原始段落数一致 |
| xml_para_index唯一性 | 索引冲突 | 同一`doc_id`下`xml_para_index`无重复（数据库唯一索引强制） |
| 表格合并结构还原 | 合并单元格 | 抽样10份含合并单元格的表格，还原后视觉效果与原docx一致 |
| 图片提取完整性 | 图片提取率 | docx内`media/`目录图片与`figures`表记录数一致（允许因格式过滤如wmf产生的合理差异） |
| 图文块裁切覆盖率 | figure_with_context生成率 | 全部含图/表段落均生成对应chunk，无遗漏 |
| 解析降级不阻断 | 单点故障隔离 | 单段落/单图片解析异常不导致整份文档解析失败 |
